GptScaled - how it works
========================

Notes on gpt_scaled: the model it trains, how each batch is shared between
the GPU and the CPU, and the two engines that do the arithmetic - the blocked
AVX2 multiply on the CPU and the CUDA kernels on the GPU. Written 2026-10-09
from the code in this directory; file and function names refer to this
directory's copies.


1. The scale-up
---------------

1.1 The model

The character-level GPT that Karpathy's "Let's build GPT" video ends on,
trained on tiny shakespeare (makemore/input.txt). The vocabulary is the set
of distinct bytes in the corpus: 65.

    n_embd    384   channels per position (C)
    n_head    6     heads of 64 channels each (hs)
    n_layer   6     Transformer blocks
    block     256   context: positions per window (T)
    batch     64    windows per step (B)
    dropout   0.2
    lr        3e-4  AdamW (betas 0.9 / 0.999, weight decay 0.01)
    steps     5000, evaluated every 500 on 200 batches of each split

These are the kBig* constants, kIters and kEvalIters in gpt_model.h, and
kEvalEvery in gpt_scaled.cpp.

One window, from characters to loss:

    tokens                                  T ints
    x = wte[token] + wpe[position]          T x 384
    6 x Block                               T x 384
    LayerNorm (ln_f)                        T x 384
    lm_head: Linear 384 -> 65               T x 65 logits
    cross entropy against the next character at every position

Every position of a window is a training example of its own: position t
predicts character t+1 from characters 0..t. A batch is therefore
64 x 256 = 16,384 predictions.

A Block is pre-norm, with two residual adds (row vectors, so x W):

    x = x + Dropout(Attention(LN1(x)) Wp + bp)
    x = x + Dropout(ReLU(LN2(x) W1 + b1) W2 + b2)       384 -> 1536 -> 384

Attention runs all six heads out of one 384 x 384 projection each for Q, K
and V (no bias). Head h owns channels [64h, 64h + 64) of each:

    scores = Q_h K_h^T / sqrt(64)           T x T
    causal mask: position t sees only 0..t (the future gets zero probability)
    P      = softmax of each row, then dropout
    out_h  = P V_h                          T x 64
    the six out_h side by side are the 384 channels that Wp projects

Initial weights are normal(0, 0.02) everywhere and biases zero - the video's
_init_weights.

Parameters, 10,788,929 in all (the video prints 10.788929 M):

    wte  65 x 384                                  24,960
    wpe  256 x 384                                 98,304
    one block                                   1,773,312
        Wq, Wk, Wv, Wp   4 x 384 x 384               589,824
        bp                                               384
        W1 384 x 1536 + b1                           591,360
        W2 1536 x 384 + b2                           590,208
        ln1, ln2 (gamma and beta)                      1,536
    6 blocks                                   10,639,872
    ln_f                                              768
    lm_head 384 x 65 + 65                          25,025

One step costs about 1.11 TFLOP (step_flops): two multiply-adds per weight
per prediction going forward and twice that going back (the usual 6N), plus
attention's two T x T products, which at context 256 are about 5% of the
total. The 5000 steps come to about 5.5 PFLOP.

The learned position table has two consequences. The context can never exceed
256, because there is no row for position 257. And sampling has to crop to
the last 256 characters (see 1.6).


1.2 Two copies of the model

gpt_scaled holds the model twice, in SplitModel:

  - gpt::Gpt from gpt_model.h, on the CPU, running the blocked multiply. This
    is the master copy: AdamW updates it, it is checkpointed, and it is the
    one sampled from.
  - gpt_cuda::Model from gpt_cuda.cu, on the GPU. It is used purely as a
    forward and backward engine: it gets fresh weights before every step and
    hands gradients back. Its own AdamW is never called.

Both keep their tensors in the same order (checked in the constructor), so
weights and gradients can be walked side by side.


1.3 One training step

    1. Draw 64 random windows from the training text: x is 256 characters,
       y is the same window shifted by one.
    2. Deal them out: the first n windows to the GPU, the other 64 - n to
       the CPU.
    3. Run both halves at once. The GPU half runs on a std::async thread,
       which spends its time waiting on the device. The CPU half runs on the
       main thread with an OpenMP team one thread smaller than usual, leaving
       a core for the GPU's driver thread (kGpuDriverThreads).
    4. The GPU takes its n windows as c calls of k windows each (k <= 16).
       Its backward kernels add into the gradient buffer rather than
       overwrite it, so the c gradients pile up on the device and cross to
       the host in one copy at the end.
    5. Combine into the mean over the whole batch (combine()):

           g = (k / B) * (g_1 + ... + g_c)  +  ((B - n) / B) * g_cpu

    6. AdamW on the CPU, then the new weights to the GPU in one 43 MB copy.

Why the GPU's weight is k/B and not n/B: each call's loss is the mean over
that call's k windows, so the device holds a sum of c means. Every window
should count 1/B; inside a chunk's mean it counts 1/k; so the pile is scaled
by k/B. That only works if every chunk is the same size, so the GPU's share
is rounded down to a multiple of its chunk count (38 wanted becomes
3 x 12 = 36).


1.4 Why chunks at all

Memory. Between its forward and backward passes the GPU keeps about 85 MB of
activations per window at context 256: two thirds in (B, T, C) tensors, the
rest in the (B, heads, T, T) attention squares. The GTX 1050 Ti has 4 GB,
shared with the CUDA context and the Windows desktop. gpt_split, which hands
the GPU its whole share in one call, asked for 3.2 GB for 38 windows and ran
out. A chunk of at most 16 windows needs about 1.4 GB, and every chunk reuses
the same buffers. The weights, gradients and both Adam moments together are
only 173 MB.


1.5 Balancing the split

Every step times both halves. The time per window on each side goes into a
running average (kSmoothing = 0.25), and the GPU's share becomes

    share = cpu_s_per_window / (gpu_s_per_window + cpu_s_per_window)

which is the split at which both sides finish together. It starts at 0.6
(kInitialGpuShare, from the two bench throughputs) and settles within a few
dozen steps. Each side always gets at least one window, so that both keep
being timed. The first step is not counted, because it pays for first touch.

Evaluation (estimate_loss: 200 batches of each split, dropout off) is shared
the same way, forward passes only. The loss is the two sides' means weighted
by how many windows each saw.


1.6 What the program does, in order

    0. Load the corpus.
    1. Check the split: one forward and backward pass at the full shape
       (6 windows, dropout off, the GPU in chunks of 2) against the scalar
       reference from the same weights. The loss has to agree to 1e-4 and
       every gradient tensor to 1e-3 of its largest entry. This is what
       proves the k/B weighting.
    2. Train 5000 steps, or load the checkpoint if one is beside input.txt.
       It uses gpt_model.h's format and name, so gpt.cpp's scale-up branch
       and the chat tool find it too. Delete it to train again.
    3. Print where a step's time went: GPU half, CPU half, combining the
       gradients, AdamW plus the upload.
    4. Sample 1000 characters on the CPU, because gpt_cuda.h returns losses
       and never logits. Each character is a full forward pass over the last
       256 characters or fewer. There is no KV cache, and an exact one would
       only help the first 256 characters: once the window slides, every
       character moves one position, so its wpe row - and with it its keys
       and values in every layer - changes.


1.7 Measured

The run of 2026-10-01 on the i9-9900KF and the GTX 1050 Ti took about
3 hours: 144 minutes of training at about 1733 ms a step (about 639 GFLOP/s
for the two devices together), settling at 45 windows on the GPU (3 chunks
of 15) and 19 on the CPU, plus 39 minutes of evaluations. Validation loss
bottomed at 1.4764 at step 2500, then rose to 1.5615 by the end while the
training loss kept falling - overfitting - so the 1.48 check failed. That run
predates the fix to the GPU's dropout seeds (see 3.6).


2. The vectorised CPU multiply (gpt_gemm.h), in a nutshell
----------------------------------------------------------

2.1 What it replaces

Nearly all of the arithmetic is matrix multiplication: every Linear layer
(out = x W + b forward; dx = dout W^T and dW += x^T dout backward) and
attention's products for each (batch, head). gpt_model.h writes these as
plain loops - for each row, for each input channel, add a scaled row of W.
That threads well but runs at a few percent of the chip, for two reasons:

  - each row of x streams the whole weight matrix through the cache, so the
    loops wait on memory;
  - MSVC was not turning the loops into vector code (measured: /arch:AVX2,
    and switching double to float, changed nothing).

Setting gpt::active_kernels() = Kernels::kBlocked sends those multiplies to
blocked::gemm instead. The walkthrough stays on kScalar.


2.2 The interface

    gemm(trans_a, trans_b, m, n, k, alpha, A, lda, B, ldb, C, ldc, may_thread)

    C (m x n) += alpha * op(A) * op(B)

Row-major, with a transpose flag per operand, and it always adds into C. Row
strides may be wider than the row, which is how attention passes one head's
64-channel slice of a 384-channel tensor without copying it.


2.3 Blocking: the GotoBLAS / BLIS scheme

The multiply is cut into pieces sized to each cache level, and each piece is
copied ("packed") into exactly the order the innermost loop will read it:

    for each 3072-column slab of B (NC)
      for each 256-deep slice of k (KC)
        pack B (KC x NC) into 16-column slivers      3 MB, lives in L3
        for each 120-row block of A (MC)
          pack A (MC x KC) into 6-row panels         120 KB, lives in L2
          for each sliver (16 columns) and panel (6 rows)
            micro-kernel: C tile (6 x 16) += panel (6 x KC) * sliver (KC x 16)
                                                     a sliver is 16 KB, in L1

Packing pays for itself. It turns strided or transposed reads into one
sequential stream; it absorbs the transpose flags, so A*B, A*B^T and A^T*B
all run the same inner code; and it pads the edges with zeros, so the
micro-kernel always computes a full 6 x 16 tile. A tile hanging off the edge
of C is computed into a scratch tile and only its valid part added in.


2.4 The micro-kernel (AVX2 + FMA)

AVX2 has sixteen 256-bit registers of 8 floats each. The tile uses 15:

    12  accumulators: 6 rows of C x 2 vectors of 8 = the 6 x 16 tile
     2  the current row of the B sliver (16 floats)
     1  one element of A, broadcast to all 8 lanes

Each step along k is 2 loads, 6 broadcasts and 12 fused multiply-adds -
192 flops for 8 memory operations. After KC steps the tile is scaled by
alpha and added into C. The accumulators are twelve named variables rather
than an array, so that the compiler keeps them in registers for the whole
loop.

It is compiled in only for float, and only when AVX2 and FMA are available
(/arch:AVX2 on MSVC, -march=native on clang). Anything else - including a
double build - gets a portable version of the same 6 x 16 tile in plain
loops.


2.5 Threads and determinism

With OpenMP the team packs one B slab together (each thread some of the
slivers), waits at a barrier, then splits the (A block, B sliver) pairs into
contiguous runs, one per thread. Pairs rather than whole A blocks, because a
weight gradient has only 384 rows - 4 blocks, too few for 16 threads. A
second barrier keeps anyone from repacking B while it is still being read.

Every element of C is written by exactly one thread, adding its KC slices in
order, so the result is bit for bit the same whatever the team size. It is
not bit for bit the scalar loops' result (FMA and blocked summation), only
equal to float rounding.

Multiplies under 262,144 multiply-adds stay on the calling thread.
Attention parallelises over (batch, head) itself and calls gemm with
may_thread = false from inside that loop. The packing buffers are
thread_local and grow to the largest multiply each thread has seen.

The rest of the CPU model (LayerNorm, ReLU, residual adds, cross entropy) is
plain OpenMP over rows, with sums kept in a fixed order. The dropout mask and
the embedding-gradient scatter stay serial on purpose.


2.6 Measured

On the i9-9900KF (8 cores, 16 threads), at 384 channels / 6 heads / 6 layers,
context 64, batch 16 (gpt_blocked): 208 ms a step against 1531 ms for the
threaded scalar loops - 7.3x, 319 GFLOP/s, about a quarter of the chip's
float peak. On the 32-channel walkthrough model it is only 1.43x: with loops
8 to 128 long, there is too little to vectorise.


3. The CUDA model (gpt_cuda.cu), in a nutshell
----------------------------------------------

3.1 The boundary

gpt_cuda.h is plain C++: a Model class with an opaque Impl that speaks
std::vector<float>. Everything CUDA lives in gpt_cuda.cu, so nvcc never
compiles gpt_model.h and the host code never sees a CUDA type. The interface
is load weights, forward_backward / forward_loss, read_grads, zero_grad,
set_training, adamw_step and sync. Float only: the GTX 1050 Ti runs double at
1/32 of its float rate.


3.2 Memory

All parameters live in one flat device buffer, and so do the gradients and
both Adam moments, in the same tensor order as gpt::Gpt. zero_grad is one
memset, AdamW is one launch over 10.8M elements, and weights in or gradients
out are one memcpy each.

Each block keeps what its backward pass needs (BlockActs: the LayerNorm
outputs and inverse deviations, Q, K, V, the attention probabilities, the
dropout masks, the feed-forward's hidden layer, and so on). The backward
scratch is shared by all six blocks, since only one runs backward at a time.
Buffers grow to fit the largest call and never shrink - which is why
gpt_scaled bounds the size of a call.


3.3 Three kinds of kernel

  - Elementwise, one thread per element: the embedding lookup, ReLU, the
    residual adds, dropout, AdamW.
  - One warp (32 threads) per row: LayerNorm forward and backward, the causal
    softmax forward and backward, cross entropy. A row is at most a few
    hundred numbers. Each lane takes every 32nd element, and the lanes
    combine their sums and maxima with __shfl_xor_sync butterflies, without
    touching shared memory.
  - The matrix multiply, where the time goes.


3.4 The multiply (gemm_kernel)

The textbook shared-memory tiled SGEMM:

  - A block of 16 x 16 = 256 threads owns a 64 x 64 tile of C.
  - It walks k in steps of 16. At each step the block loads a 64 x 16 slab
    of A and a 16 x 64 slab of B into shared memory, each padded by one
    column against bank conflicts. The loads follow the operand's stored
    order, so neighbouring threads read neighbouring addresses even when the
    operand is transposed.
  - Each thread accumulates a 4 x 4 piece of the tile in registers: for each
    of the 16 k values it reads 4 values of A and 4 of B from shared memory
    and does 16 fused multiply-adds. The piece is strided (rows ty, ty+16,
    ty+32, ty+48, and likewise columns), so a warp reading the slab hits
    consecutive words.
  - At the end the tile is scaled by alpha, gets a per-column bias if one was
    given, and is written into C or added to it.
  - The two transpose flags are template parameters (four instantiations),
    so the inner loop has no branches.
  - It is batched: blockIdx.z picks a (batch, head) pair, and per-operand
    strides say where that pair's matrices start. Each of attention's
    products is one launch covering all 64 x 6 (batch, head) pairs, with each
    head addressed as a 64-column slice of a (B, T, C) tensor - no copies.

It is gpt_gemm.h's idea one level down: shared memory plays the packed
L1/L2 blocks, and registers play registers.


3.5 Attention on the GPU

Forward: three gemms for Q, K and V; one batched gemm for the scores of every
(batch, head); the causal softmax in place (a warp per row, the future set to
zero); dropout; one batched gemm of P by V; then the Wp projection with its
bias folded into the gemm. As on the CPU, the full T x T square is computed
and the masked half discarded, in exchange for plain rectangular multiplies.
The backward pass mirrors it with four more batched gemms and a softmax
backward.


3.6 The same bits every run

The usual GPU shortcut, atomicAdd into a shared total, makes the result
depend on scheduling. This code avoids it, as the CPU threading does:

  - Column sums (biases, LayerNorm gamma and beta, the position table's
    gradient): fixed chunks of 64 rows first, then the chunks added in order.
  - The token embedding's gradient, where many positions share one row: the
    host counting-sorts the positions by token, and one block per vocabulary
    row adds up its positions in order.
  - The loss: per-row losses are copied back and summed in order on the host.
  - Dropout: no shared random generator. Each element's keep-or-drop comes
    from hashing (seed, element index) with splitmix64's finaliser, so the
    threads share no state. Every mask gets a new seed, and the seeds are
    themselves passed through the same hash. Before that fix, successive
    seeds were a fixed constant apart, which made each mask the previous one
    shifted by one element.


3.7 Ordering and errors

Every kernel runs on the default stream, so each sees the finished output of
the one before it with no explicit synchronisation. The host waits only when
it reads something back (the loss, the gradients) or calls sync(). Every CUDA
call and launch is checked (CUDA_CHECK, CHECK_LAUNCH), and a failure throws.

The backward kernels add into the gradient buffer rather than overwriting it.
That is the property gpt_scaled's chunking relies on.


3.8 Hardware and measured speed

GTX 1050 Ti: Pascal, sm_61, 6 SMs, 4 GB. It needs CUDA 12.x, since CUDA 13
dropped Pascal. At the bench shape (384 / 6 / 6, context 64, batch 16) it
ran 132 ms a step, 504 GFLOP/s - 1.58x the blocked CPU multiply, about a
quarter of the card's float peak. In gpt_scaled, at context 256, it settled
at about 70% of each batch (45 of 64 windows).
